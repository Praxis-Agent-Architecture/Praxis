# agentCore Spec / Class 声明模型 v1

## 1. 定位

本文是 `Praxis_Agent_Architecture/docs/agentCore/agentCore_rebase_phase_1/agent-core-host-design-baseline-v1.md` 的下钻文，只定义 `agentCore` 的声明对象模型，不重复宿主基线的上层原则，也不展开源码重构方案。

本文要回答的是：用户如何声明一个 `agentCore`，这些声明如何被分层、复用、编译，最后变成运行时可拉起的 `runtime-table`。

本文不冻结以下内容：

- `auth` 管理层的实现
- 四大官方模块的内部行为细节
- provider / carrier 的具体协议形状
- `runtime-table` 的字段 schema、序列化格式和导出格式
- 具体 DSL 关键字、具体 JSON 字段名、完整 schema

本文先定义对象模型和编译方向，后续的小管理系统再承接声明注册、`OAO` 复用和编译产物管理。

## 2. 双层对象：Spec 与 Class

`AgentCoreSpec` 和 `AgentCoreClass` 是双层模型，不是二选一。

### 2.1 Spec

`Spec` 偏向“我要什么、边界在哪里、默认约束是什么”。

它描述的是一个 `agentCore` 声明的可检查目标，而不是运行时代码本体。一个 `Spec` 应该能被读取、验证、编译，并作为运行时装配的输入。

`Spec` 关注的重点包括：

- 这个 agentCore 面向哪些模型适配范围
- 允许引用哪些 PromptPack
- 默认开放哪些能力
- 对外暴露哪些 Interface
- 哪些约束是默认值，哪些约束是硬边界

### 2.2 Class

`Class` 偏向“如何继承、覆写、组合这一类声明”。

它不是运行时代码实现体本身，也不是宿主内部执行器。`Class` 更像声明族的组织层，用来表达“这一类 agentCore 声明应该如何复用和派生”。

`Class` 关注的重点包括：

- 基于哪个 `Spec` 或声明基座继续派生
- 哪些块可以继承
- 哪些块允许覆写
- 哪些块允许组合
- 组合后的有效声明如何被编译器展开

### 2.3 关系

`Spec` 和 `Class` 的关系不是“选一个”，而是“分两层用”。

- `Spec` 负责定义语义边界和默认装配目标
- `Class` 负责定义声明家族的复用、扩展和变体

换句话说，`Spec` 解决“声明什么”，`Class` 解决“这一组声明怎么长出来”。

## 3. 声明优先，而不是静态模板优先

用户默认是在做声明式编程。

也就是说，用户通常不是先写一份死板模板，再被系统强行套住；而是先声明目标和边界，再由系统把这些声明编译成可运行的装配结果。

高级用法允许：

- `override`：在明确边界内改写某些声明块
- `compose`：把多个声明源组合成一个有效声明
- `extend`：从已有声明族派生出新声明

这意味着系统不能被设计成只能静态套模板，也不能把所有东西冻结成单一路径。`Class` 的价值就是保留这种可迭代、可派生、可复用的空间。

## 4. 用户声明的四大板块

一个用户声明的 `agentCore`，至少会覆盖四块核心内容。

### 4.1 模型适配范围

这块描述这个 `agentCore` 面向哪类模型适配面。

它不是具体 provider 协议细节，而是声明层的范围选择，常见语义包括：

- 单一厂商
- 多厂商
- `auto`

这里的重点是“适配边界”，不是“最终用哪个 API 字段发请求”。

### 4.2 PromptPack 引用

这块描述这个 `agentCore` 引用哪些 PromptPack。

PromptPack 可以来自一个或多个声明源，且需要区分不同边界，例如：

- 治理侧
- 任务侧
- 上下文侧

这说明 PromptPack 不是单一大文本，而是可组合、可分层引用的提示包集合。声明层只负责引用关系和边界语义，不负责把不同来源硬拼成一个不可拆的长字符串，也不在这里冻结具体文件类型。

### 4.3 基本能力开放

这块描述这个 `agentCore` 默认开放哪些能力。

能力来源可落在：

- API
- SDK
- CLI

能力开放方式按宽度模板理解，官方先保留：

- 窄
- 中
- 宽
- 全
- `custom`

这里的“宽度”表示能力开放的面有多大，不是单纯的性能档位。`custom` 允许高级用户定义同级别模板，但仍然属于声明层，不等于运行时实现逻辑。这里先给出的是语义示意，不是注册表或校验规则的最终枚举。

### 4.4 Interface 开放

这块描述这个 `agentCore` 面向哪些对外接口形态开放。

可表达的方向包括：

- single-agent
- multi-agent
- cmp
- tap
- mp
- custom

这里的 Interface 关注的是“这个声明族是否允许以某种接入面被使用”，不是把某个官方模块的内部状态机提前写死。这里列的是接入面示意，不是最终固定清单。

## 5. OAO 复用方式

本文中的 `OAO` 只作为对象装配组织方式理解。

它的作用不是发明新的运行时，而是让 `Spec` 和 `Class` 的声明层在装配阶段能够被稳定组织。

可以把它理解为三件事：

- `Spec` 提供基座语义
- `Class` 提供派生组织方式
- 装配阶段把二者展开为有效声明

因此，`OAO` 复用方式应该支持：

- 复用已有 `Spec`
- 从已有 `Class` 派生新 `Class`
- 合并多个声明块
- 对特定块做局部覆写

这里的复用不是“复制一份配置”，而是“在声明模型中保留可追踪的继承关系”。

## 6. compile 到 runtime-table

声明模型最终要落到 `runtime-table`。

### 6.1 编译前

用户看到的是声明板块：

- 模型适配范围
- PromptPack 引用
- 基本能力开放
- Interface 开放

这些内容可以分散在多个 `Spec` 和 `Class` 里，但在编译前它们仍然是声明，不是运行时结果。

### 6.2 编译中

编译器负责把声明展开成有效装配结果，核心工作是：

- 解析继承、覆写和组合
- 解析 PromptPack 的引用关系
- 解析能力开放面
- 解析 Interface 开放面
- 计算默认约束与最终约束

编译阶段的目标不是执行 agent，而是把“声明的意图”变成“运行时可用的装配表”。

### 6.3 runtime-table

`runtime-table` 是编译后的正式产物。

它应该能被运行时按表拉起 `agentCore`，也应该能被检查、导出和审查。换句话说，`runtime-table` 是编译结果，不是临时中间变量。

### 6.4 轻量流程

下面这条只是一条最轻的串联示意，不定义中间格式细节。

```text
用户声明板块
  -> Spec / Class 组织
  -> compile
  -> runtime-table
  -> boot
```

如果要再细一点，可以理解为：

```text
声明输入
  -> 语义归一
  -> 继承/覆写/组合展开
  -> 有效装配结果
  -> 运行时按表启动
```

## 7. 与现有实现锚点的关系

本文只把现有仓库中的名词当作“现实锚点”，不把它们绑成新标准的最终形状。

从当前锚点看：

- `src/agent_core/goal/*` 已经体现了“source -> normalized -> compiled”的三段式思路
- `src/agent_core/runtime.ts` 已经承担了把编译后目标带入运行态的职责
- `src/agent_core/types/*` 已经给出了一批运行态、目标和事件的基础名词

这些都说明“先声明、再编译、再运行”是正确方向，但本文不把这些旧实现直接当成新 `agentCore` 的冻结标准。

## 8. 后续会有的小管理系统

后续还会有一个小管理系统，用来管理：

- 声明
- 注册
- `OAO` 复用
- 编译产物

但本文不定义它的实现细节，只定义这个管理系统将要管理的对象是什么。

这意味着后续实现者的第一步不是先做复杂管理面，而是先把 `Spec`、`Class`、声明板块和 `runtime-table` 的对象边界落清楚。

## 10. 结论

这份文档把 `agentCore` 的声明模型定在一个可迭代的位置上：

- `Spec` 负责“我要什么、边界在哪里、默认约束是什么”
- `Class` 负责“如何继承、覆写、组合这一类声明”
- 用户默认走声明式编程
- 高级用法允许 `override` / `compose` / `extend`
- 四大声明板块是模型适配范围、PromptPack 引用、基本能力开放、Interface 开放
- 声明最终要编译成 `runtime-table`
- 运行时按表拉起 `agentCore`

后续实现应围绕这条线继续细化，而不是把系统缩回成静态模板或单层配置。
