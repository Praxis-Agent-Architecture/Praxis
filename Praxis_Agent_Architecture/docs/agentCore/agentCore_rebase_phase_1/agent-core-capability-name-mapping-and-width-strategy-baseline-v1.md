# agentCore 能力名、映射表与宽度策略基线 v1

## 1. 定位

本文是 `Praxis_Agent_Architecture/docs/agent-core-host-design-baseline-v1.md` 中“能力系统”一节的下钻基线文，也是 `Praxis_Agent_Architecture/docs/agent-core-spec-class-declaration-model-v1.md` 与 `Praxis_Agent_Architecture/docs/agent-core-promptpack-semantics-and-provider-carrier-mapping-baseline-v1.md` 在能力板块上的补充文档。

本文只冻结 `agentCore` 第一版能力系统的中心模型：

- 为什么用户默认按能力名调用
- 映射表负责什么、不负责什么
- 宽度策略到底控制什么
- 默认解析应当如何面向 provider / carrier 收敛
- 用户在需要时如何显式覆写默认解析

本文不讨论源码重构计划，也不把当前仓库里的任一旧实现直接等同为最终标准实现。

本文不冻结以下内容：

- 最终注册表 schema
- 精确 resolver 接口
- 完整 override 语法
- 完整 DSL 关键字
- gateway 的最终实现细节
- 具体 provider 适配器内部的 lower 细节

第一版的目标不是一次性发明完整能力语言，而是把后续实现必须围绕的设计地基固定下来。

## 2. 上位基线承接

结合宿主总纲与声明模型，能力系统第一版已经有以下上位结论，这里直接承接，不再重复展开证明：

- 能力系统采用“能力名 + 映射表 + 宽度策略”的中心模型。
- 用户默认按能力名调用，不默认按具体 provider / carrier 名称调用。
- 映射表只负责把“能力名 + 宽度策略”解析成可执行路径，不替代宿主协议本身。
- 官方宽度模板先冻结为 `窄 / 中 / 宽 / 全`，并允许同级 `custom`。
- `Spec / Class` 处于声明与复用层，能力系统处于“最终能调用什么、怎样解析”的装配层。

因此，本文要补足的不是宿主是否采用能力名，而是“能力名之后的解析基线应当怎么长”。

## 3. 中心模型

### 3.1 能力名是默认用户面

`agentCore` 第一版中，用户默认看到和声明的是能力名，而不是某一家 provider 的 carrier 名称。

换句话说，用户通常表达的是：

- 我要生成
- 我要搜索
- 我要调用某种工具能力
- 我要走某种 agent 级能力

而不是默认表达成：

- 强制走某家 API
- 强制走某个 SDK surface
- 强制走某个 CLI-agent

这样设计的目的，是让宿主先稳定在“我想做什么”这一层，而不是让用户一开始就被迫记住各家接口壳子的差异。

### 3.2 能力来源可以多样，但默认可见面仍是能力名

能力的实际来源可能来自多种 carrier 或执行承载面，包括但不限于：

- API
- SDK
- CLI-agent
- 自定义来源

这些来源可能来自不同 provider，也可能来自同一 provider 的不同 carrier。它们属于“实现承载面”，不是默认用户面。

这里需要补一层术语对齐：上位文档常把这一类来源统称为 `CLI carrier`；本文写 `CLI-agent`，指的是 `CLI carrier` 里更偏 agent 化的一类高层承载面。也就是说，本文没有改动 carrier 分类体系，只是在能力解析语境里把这一类更具体地叫出来。

第一版能力系统必须承认这种现实：

- 同一个能力名，可能在多家 provider、多个 carrier 上都有实现。
- 同一个能力名，也可能只有某一家 provider 或某一类 carrier 才真正可用。
- 某些能力看起来名字相近，但开放范围、权限边界、降级语义并不相同。

因此，系统不能把“能力名”和“具体 carrier”混成同一层。

### 3.3 中心三件套

能力系统第一版由三件核心对象共同组成：

- `能力名`
- `映射表`
- `宽度策略`

可以把它理解为：

```text
用户声明能力名
  + 当前宽度策略
  -> 映射表解析
  -> provider / carrier 可执行路径
```

其中：

- 能力名负责表达“要什么能力”
- 宽度策略负责表达“这次要开放到多宽的实现面”
- 映射表负责把前两者解析到现实可执行路径

## 4. 宽度策略的含义

### 4.1 宽度不是单纯“能力多少”

第一版里，“宽度”不是一个抽象强弱标签，也不是单纯“能力越多越宽”的数量概念。

宽度至少同时包含三层含义：

- 能力开放范围
- carrier 解析优先级
- 允许的降级路径

白话讲，宽度控制的不是“开几个开关”而已，而是这次调用默认愿意把门开到多大、优先先试哪一类通道、如果首选路径不可用时是否允许往别的面回退。

### 4.2 官方宽度模板

第一版官方宽度模板冻结为以下四档：

- `窄`
- `中`
- `宽`
- `全`

同时允许存在同级 `custom` 模板，但 `custom` 不计入官方四档本身；其注册机制不由本文定义。

### 4.3 默认优先级方向

第一版必须明确以下默认方向：

#### 窄

`窄` 的默认方向是优先 `API`。

它表达的是更收敛、更可控、更少开放面的默认路线。这里冻结的是“优先偏向 API，且默认开放面较窄”的方向，不把所有能力的实际命中顺序写死；具体如何命中，仍由映射表结合该能力的现实可用面来决定。

#### 中

`中` 的默认方向是优先 `SDK`，若无则回 `API`。

它表达的是在更完整宿主能力与相对可控开放面之间做平衡。这里冻结的是“优先偏向 SDK，无则可回 API”的方向；具体如何命中，仍由映射表结合该能力的现实可用面来决定。

#### 宽

`宽` 的默认方向是优先 `CLI-agent`，无则逐级降级。

这里冻结的不是一条对所有能力一刀切的 resolver 固定顺序，而是：

- `宽` 默认允许更大的开放面
- `宽` 默认偏向 `CLI-agent`
- 若首选路径不可用，允许向更收敛的承载面逐级回退

具体先命中哪条 `CLI-agent / SDK / API` 路径，仍由映射表结合某个能力的现实可用面来决定。

#### 全

`全` 的默认方向是允许最广 carrier 参与，并允许更大的开放面。

它不是“永远选最强实现”的口号，而是表达：

- 解析阶段可以考虑最广的 carrier 集合
- 默认开放范围可以比 `宽` 更大
- 允许接入未来新增的更厚 carrier 或组合 carrier

`全` 的价值在于给最高开放度场景保留合法位置，而不是把所有日常调用都默认推到这一档。

同样地，`全` 冻结的是“允许更广 carrier 参与与更大开放面”的边界，不把具体命中顺序写成所有能力统一适用的固定梯子；具体解析仍由映射表结合现实可用面来完成。

#### custom

`custom` 表示用户可注册同级模板。

它的职责不是破坏官方模板，而是允许高级用户在不改写能力名模型的前提下，自定义：

- 开放范围
- carrier 优先顺序
- 允许的降级方向

本文只冻结“可以有同级 custom 模板”这一点，不冻结模板注册与校验细节。

## 5. 映射表的职责边界

### 5.1 映射表负责什么

映射表的职责，是把“能力名 + 当前宽度策略”解析到现实可执行路径。

它至少要能承接以下判断：

- 这个能力名当前有哪些 provider / carrier 可用
- 在当前宽度下，优先顺序是什么
- 当前 provider / carrier 是否属于允许开放面
- 首选路径不可用时，是否允许降级，降到哪里

这意味着映射表本质上是能力解析层，不是宿主总协议的替代品。

### 5.2 映射表不负责什么

映射表不应承担以下职责：

- 不替代 `Spec / Class` 的声明模型
- 不替代 `PromptPack` 的语义层
- 不替代宿主协议本身
- 不把 gateway 直接定义成唯一真相
- 不强行把所有 provider / carrier 压成一个字段 schema

白话讲，映射表负责“给你找路”，不负责“重新定义整个国家地图”。

### 5.3 映射表与现实代码锚点的关系

从当前仓库的现实形状看，已经可以看到若干只读锚点：

- `src/agent_core/capability-types/capability-manifest.ts` 中有 `CapabilityManifest` 与 `CapabilityBinding`
- `src/agent_core/capability-types/capability-gateway.ts` 中有 `CapabilityAdapter`、`CapabilityPool`、`KernelCapabilityGateway`
- `src/agent_core/capability-gateway/kernel-capability-gateway.ts` 说明 gateway 当前只是 `acquire / prepare / dispatch / cancel` 的桥
- `src/rax/adapters.ts` 聚合了多家 provider 的 capability adapter descriptors，当前既含 API 来源，也含 agent 来源
- `src/rax/runtime.ts` 通过 `CapabilityRouter + adapters + compatibility profile` 形成默认 runtime
- `src/rax/registry.ts` 已经存在 `providerSupport / preferredLayer / defaultLayer` 这一类“能力名 -> provider/layer”的现实形状

这些锚点说明，Praxis 当前代码里已经存在“能力注册、路径选择、适配器装配、桥接执行”的现实骨架。

但本文只把它们当作设计证据，不把它们冻结成最终 schema 或最终接口标准。

## 6. 默认解析与 override

### 6.1 默认解析原则

第一版中，默认解析必须遵守以下顺序：

1. 用户先按能力名表达意图。
2. 系统结合当前宽度策略确定可接受开放面。
3. 映射表在可接受开放面内解析 provider / carrier 路径。
4. 若首选路径不可用，再按该宽度允许的降级方向回退。

因此，默认解析的主语始终是“能力名”，而不是“某个 provider 的某个 carrier 名称”。

### 6.2 可用面收窄

如果某个能力并不是多家多 carrier 普遍具备，默认映射不应假装它有一整个对称矩阵。

正确做法是：

- 先承认该能力的现实可用面
- 再把映射结果收窄到真正存在的 provider / carrier 路径

也就是说，默认解析可以收窄，但默认用户面仍然应当是能力名。

### 6.3 override 的地位

虽然默认写法应当按能力名调用，但高级用户如果明确想要某个 carrier 的特定实现，系统必须允许显式覆写默认解析。

允许的方向至少包括：

- 显式 override
- 注册自定义宽度模板
- 用更精确的声明表达能力路径偏好

这样设计的重点在于：

- 默认用户面保持简单
- 高级用户仍能在必要时精确控路

### 6.4 override 的作用边界

override 的作用，是覆写默认解析，不是废弃能力名模型。

换句话说，即便用户点名某个 carrier，这个动作也应理解为“在能力名模型之上施加更具体约束”，而不是让系统退化成“以后大家都直接写 provider/carrier”。

## 7. 白话例子

### 7.1 公共能力在多家多 carrier 都有

假设“生成文本”这一类公共能力，同时在多家 provider 的 API 与更高层 carrier 上都存在。

默认情况下，用户只写能力名，系统再根据当前宽度策略走映射表：

- `窄` 时优先收敛到 API
- `中` 时优先尝试 SDK，无则回 API
- `宽` 时默认偏向 CLI-agent，但是否直接命中 CLI-agent、还是收敛到 SDK / API，仍由映射表结合该能力的现实可用面决定

用户不需要一上来就写“请走哪一家哪一层”，因为这些分歧默认由映射表结合该能力的现实可用面来消化。

### 7.2 只有某一家或某一类 carrier 才有

假设某个能力只在某一家 provider 的某个高层承载面上存在，别家没有，或者 API 层没有。

这时默认映射的正确行为，不是伪造一个“到处都能用”的假象，而是把可用面自然收窄到真实存在的路径。用户依然按能力名表达，但映射结果会收敛到真正可用的那一家或那一类 carrier。

### 7.3 用户明确点名特定 carrier

假设用户明确要求“就走某个 CLI-agent 实现，不要自动回 API”。

这时系统应允许通过 override、自定义模板或更精确声明来固定解析路径。也就是说，默认解析可以被覆写，但覆写是显式行为，而不是默认行为。

- `Spec / Class` 决定如何声明与复用
- `PromptPack` 决定提示与语义块

## 9. 当前不冻结的内容

为了给后续能力子系统实现保留空间，本文明确不写死以下细节：

- 最终能力注册表 schema
- 精确 resolver 接口
- 映射表的最终序列化格式
- 完整 override 语法
- 完整 DSL 关键字
- gateway 的最终实现结构
- provider/carrier 适配器内部的最终 lower 细节
- 宽度模板注册与校验机制
- 能力名到运行时 binding 的最终编译链路格式

这意味着后续实现者的重点，不是先争论最终字段名，而是先围绕本文冻结的三件事推进：

- 默认用户面是能力名
- 默认解析依赖映射表
- 宽度策略同时控制开放范围、优先级与降级路径

## 10. 结论

`agentCore` 能力系统第一版的稳定结论可以压缩为六点：

- 能力系统采用“能力名 + 映射表 + 宽度策略”的中心模型
- 用户默认按能力名调用，不默认按 provider / carrier 名称调用
- 能力来源可以来自 API、SDK、CLI-agent 以及自定义来源，但默认用户面仍是能力名
- 映射表负责把“能力名 + 当前宽度策略”解析成可执行路径，不替代宿主协议本身
- 宽度不仅表示能力开放多少，也表示开放范围、carrier 优先级和允许的降级路径
- 用户若明确需要特定 carrier，可以通过 override、自定义模板或更精确声明覆写默认解析

后续能力子系统的注册、resolver、gateway、runtime 装配与检查能力，都应围绕这份基线继续细化，而不是反过来让某个现有适配器或某个当前接口壳子决定能力系统的总边界。
