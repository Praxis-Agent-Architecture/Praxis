# agentCore 宿主设计基线 v1

## 1. 背景与目标

本文只定义新一代 `agentCore` 的宿主设计基线，不讨论源码重构，也不把现有 `src/agent_core` 当作整理后续版。

- 新 `agentCore` 不是现有 `src/agent_core` 的整理版，而是新的宿主核心标准。
- 新 `agentCore` 第一版落位于 `Praxis_Agent_Architecture/` 中建设，并按“独立可构建 package”的思路建设；现有混合代码只作为只读参考，不作为新标准的直接写入目标。
- 第一版采用 `TypeScript` 宿主 + 正式 `DSL`，不是独立新语言。
- 更独立的语言层是否抽出，留待后续设计，不在本文冻结。

本文的目标不是画愿景图，而是给后续实现、拆分和审查提供稳定的设计基线。

## 2. 核心原则

### 2.1 宿主先行

`agentCore` 首先是宿主协议和装配标准，不是单纯的代码整理层。

### 2.2 语义先于字段

对外先定义语义层，再决定具体 carrier 字段映射。不要先被某一家 API 形状绑死。

### 2.3 能力名优先

用户先按能力名调用，内部再解析到具体 provider / carrier。

### 2.4 规格与实现分层

采用 `Spec + Class` 双层 `OAO` 模型：

- `Spec` 层负责定义约束、协议、装配要求和可检查边界。
- `Class` 层负责具体实现、组合方式和运行时承载。

这里的 `OAO` 只作为对象装配组织方式使用，不在本文展开额外解释。

### 2.5 冻结宿主协议，不冻结模块内部行为

第一版冻结的是宿主协议和接入方式，不是四大官方模块的内部行为系统。

## 3. 中心对象

### 3.1 agentCore

`agentCore` 是新宿主核心标准的名字。它负责把能力、提示包、 carrier、运行态和模块接入方式统一起来。

### 3.2 Spec

`Spec` 是对外和对内都可检查的规格对象，强调“应该是什么”。

### 3.3 Class

`Class` 是落地实现对象，强调“怎么做”和“谁来执行”。

### 3.4 ModelCarrier

`ModelCarrier` 是模型承载与调用通道的总称，表示模型不只通过一种接口形状进入系统。

### 3.5 InterfacePack

`InterfacePack` 是宿主对外暴露的一组接口与接入协议的集合。它的具体条目留待接口包子系统设计时定义。

### 3.6 runtime-table

`runtime-table` 是正式装配产物，不是临时调试输出。

- 框架内部必须能导出和检查。
- 高级用户必须能导出和检查。
- 普通用户可以不直接操作它。

## 4. PromptPack

`PromptPack` 先统一语义层，再做 carrier 映射。

### 4.1 三层语义

PromptPack 的语义分三层：

- `governance`
- `task`
- `context`

这三层是统一语义层，不等于具体 provider 的字段名。

### 4.2 设计要求

- 不能直接照抄三家字段名来定义 PromptPack。
- PromptPack 先描述“这些内容属于什么语义层”，再决定如何落到具体 carrier。
- 具体 carrier 的字段映射，留待 ModelCarrier 与接口适配层定义。

## 5. 能力系统

能力系统采用“能力名 + 映射表 + 宽度策略”的结构。

### 5.1 基本形态

- 用户默认按能力名调用。
- 系统内部通过映射表把能力名解析到 provider / carrier。
- 宽度策略决定这次调用需要多宽的实现面。

### 5.2 官方宽度模板

官方先定义四档宽度模板：

- `窄`
- `中`
- `宽`
- `全`

### 5.3 自定义模板

允许用户注册同级 `custom` 模板。

- `custom` 模板和官方模板处在同一层级。
- `custom` 模板的具体约束、命名和校验规则，留待能力系统子设计定义。

### 5.4 映射表责任

映射表只负责把“能力名 + 宽度策略”解析为可执行路径，不替代宿主协议本身。

## 6. ModelCarrier

`ModelCarrier` 采用双轨并重，不把系统锁死在单一接口形状上。

- `API` carrier 进入正式规划。
- `SDK` carrier 进入正式规划。
- `CLI` carrier 进入正式规划。

这意味着系统后续要同时支持多种承载方式，而不是只围绕单一 vendor API 写死。

### 6.1 设计边界

- 不能被 OpenAI 单一接口形状绑死。
- 不同 carrier 可以有不同适配方式，但必须回到同一套宿主语义。
- carrier 的细节协议，留待各 carrier 子系统设计时定义。

## 7. InterfacePack

`InterfacePack` 是宿主对外的接口打包层，负责把用户可见的入口、能力调用、运行态导出与检查能力组织起来。

本文只冻结它的角色，不冻结它的全部字段。

- 它要能承接能力名调用。
- 它要能承接 PromptPack 的语义层。
- 它要能承接 runtime-table 的导出与检查。
- 它要能把 provider / carrier 的差异挡在宿主内部。

具体接口列表、命名和文件拆分，留待接口包子系统设计时定义。

## 8. runtime-table

`runtime-table` 是宿主装配后的正式结果，属于一等产物。

### 8.1 定位

- 它不是内部临时变量。
- 它不是仅给开发者看的私有调试产物。
- 它是框架内部、集成测试和高级用户都能检查的装配结果。

### 8.2 使用边界

- 框架内部：用于装配验证、导出、审查和对齐。
- 高级用户：用于检查当前运行态如何被装配。
- 普通用户：可以不直接接触它。

### 8.3 未冻结内容

`runtime-table` 的字段结构、序列化格式、检查维度和导出格式，留待 `runtime-table` 子系统设计时定义。

## 9. 官方模块占位

第一版里，`cmp / mp / tap / multiAgent` 先作为官方模块占位和接入协议来看，不提前写死它们的内部行为系统。

### 9.1 cmp

`cmp` 先作为官方模块占位与接入协议存在。它的内部行为系统、默认流程和细部状态机，留待 `cmp` 子系统设计时定义。

### 9.2 mp

`mp` 先作为官方模块占位与接入协议存在。它的内部行为系统、默认流程和细部状态机，留待 `mp` 子系统设计时定义。

### 9.3 tap

`tap` 先作为官方模块占位与接入协议存在。它的内部行为系统、默认流程和细部状态机，留待 `tap` 子系统设计时定义。

### 9.4 multiAgent

`multiAgent` 不是 `agentCore` 本体，而是外部治理 / 管理系统。

- 对 `agentCore` 来说，关键问题不是它内部怎么长出来。
- 关键问题是 `agentCore` 是否开放被它接管和治理的接口。

`multiAgent` 的内部治理逻辑、管理边界和策略系统，留待 `multiAgent` 子系统设计时定义。

## 10. 现有仓库位阶说明

本文只记录当前仓库中的相对位阶，不把它们改写成新的实现方案。

- `src/agent_core` 是现有核心能力与子系统的聚合层，也是新设计的重要只读参考。
- `src/rax` 是更上层的统一门面与集成面，负责把 `agent_core` 内部能力再组织起来。
- `tap` 在当前仓库里主要体现为 `ta-pool*` / `tap-*` 这一组命名域，而不是单独顶层语言或单独宿主。
- `cmp` 和 `mp` 都属于 `agent_core` 里的子系统，同时也被 `rax` 再导出和再组织。

这份基线只承认这个位阶，不把旧实现直接当成新宿主标准。

## 11. 当前不冻结的内容

下面这些内容留待各子系统设计时定义，本文件不写死：

- `cmp / mp / tap / multiAgent` 的内部行为系统
- 各模块默认策略和调度细节
- `runtime-table` 的字段结构、序列化格式和检查维度
- `InterfacePack` 的具体接口清单和文件拆分
- 各 `carrier` 的字段映射细节
- `custom` 宽度模板的注册机制和校验规则
- 后续是否抽出更独立的语言层

## 12. 结论

这份文档冻结的是 `agentCore` 的宿主协议基线：

- 先有独立可构建的 TypeScript 宿主。
- 先有统一语义的 PromptPack。
- 先有能力名、映射表和宽度策略。
- 先有 API / SDK / CLI 的双轨 carrier 规划。
- 先有可导出、可检查的 `runtime-table`。
- 先把 `cmp / mp / tap / multiAgent` 放在正式占位与接入协议的位置上。

后续所有实现，都应以这份基线为准做增量迭代，而不是反过来让旧混合代码决定新宿主的边界。
